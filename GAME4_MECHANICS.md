## 1. Canonical simulation model

### 1.1 Acoustic graph
Each encounter owns one physical navigation layout plus an acoustic graph embedded in that layout.

**Acoustic node fields**
- `node_id`: stable unique ID.
- `world_region`: physical room/area represented by the node.
- `occupants`: player/listeners/sources currently assigned to the node.
- `is_objective_region`, `is_exit_region`: encounter flags only.

**Acoustic edge fields**
- `edge_id`: stable unique ID.
- `node_a`, `node_b`: connected nodes.
- `direction`: bidirectional by default; one-way only when a visible physical opening truly supports it.
- `base_attenuation`: integer **0–2**.
- `door_id`: optional visible door controlling connectivity/attenuation.
- `barrier_slot_id`: optional authored slot that can receive the single barrier.
- `enabled`: derived from visible world state.

No hidden acoustic edges. Every enabled edge corresponds to a visible physical passage/opening.

### 1.2 Strength and attenuation
Canonical sound strength bands are integers **1–4**. They are presentation-labeled by glyph/shape, not required numbers.

A sound event begins with `strength S` at `source_node`. For every reachable node, compute the minimum total attenuation cost across all enabled routes. Remaining intensity is:

`I(node) = max(0, S - min_route_cost(node))`.

A route with total cost >= S produces zero intensity and does not count as audible.

Baseline barrier effect: **+3 attenuation** on the occupied barrier-slot edge. This is deliberately strong but not binary: a strength-4 event can leak through at intensity 1 when no cheaper alternate route exists.

Door states may contribute either disconnected/closed or a small authored attenuation state, but every state is visibly distinguishable. Phase-5 content may use only states listed in its content schema; no arbitrary per-level hearing modifiers.

### 1.3 Multiple/equal routes
Propagation is not single-path simulation. Hearing uses the minimum attenuation value. If multiple routes tie for minimum cost, **all tied minimum routes are mechanically real and shown in prediction/resolution**. Blocking one route therefore cannot falsely imply silence when another equal route remains.

For deterministic presentation ordering only, tied routes sort by stable `edge_id`; this ordering never changes hearing outcome.

### 1.4 Listener threshold
Each listener has integer `hearing_threshold` in **1–3**. Listener hears event iff `I(listener_node) >= hearing_threshold` at event-resolution time.

Threshold is persistent and visually encoded on that listener. No hidden alertness multiplier changes hearing math. Difficulty settings may not secretly modify thresholds unless explicitly defined as a separate assisted ruleset later; baseline difficulty preserves them.

## 2. Sound-event classes

The Phase-3 vocabulary is frozen into four source families:

1. **Locomotion event** — generated by player movement state transitions; source follows player node.
2. **Deliberate distraction** — player intentionally triggers a visible world source; normal design band 2–3.
3. **Objective/environment loud action** — required or strategically meaningful interaction; normal design band 3–4.
4. **Moving environmental source** — exceptional visible source whose node changes deterministically along an authored route.

Content may choose a strength band per source instance from 1–4, but may not invent frequency/pitch categories, hearing material types or audio-only properties.

Simultaneous sound events are resolved independently from the same post-mutation graph snapshot. A listener may hear several events in one tick; reaction selection is specified below.

## 3. Player locomotion and noise states

### 3.1 Movement states
Baseline player movement states:
- `IDLE`
- `WALK`
- `FAST_MOVE`
- `INTERACTING`
- `BARRIER_MANIPULATION`
- `FAILED/LOCKED`

No crouch meter or stamina economy is required for 1.0. WALK and FAST_MOVE are enough to create a readable movement/noise tradeoff if content needs it.

Baseline noise contract:
- IDLE: no locomotion event.
- WALK: band 1 locomotion pulse at a fixed distance/time cadence.
- FAST_MOVE: band 2 locomotion pulse at a shorter cadence.
- INTERACTING: interaction instance decides whether a separate event occurs.
- BARRIER_MANIPULATION: barrier motion itself is **silent mechanically** in baseline. This prevents a recursive `moving the sound blocker makes sound` rule from obscuring the core model. Exposure, not self-noise, is its cost.

Exact cadence is a balance knob, but it is deterministic and exposed to prediction. Node transition always updates the player's source node before any locomotion pulse caused by entry into the new node.

### 3.2 Node ownership at boundaries
Physical regions own authored acoustic trigger volumes. The player belongs to exactly one acoustic node at a canonical tick. Crossing a node boundary atomically changes ownership; ties on an exact boundary resolve to the destination region determined by movement direction. The same ownership function is used by preview and actual event generation.

## 4. Barrier interaction state machine

There is one baseline barrier instance per encounter.

### 4.1 Barrier data
- `barrier_id`
- `rail_id`
- ordered authored `snap_slots[]`
- current `slot_id`
- current rail interpolation parameter
- local handle/reach volume
- orientation state when the rail supports rotation
- `state`: RESTING / GRABBED / MOVING / SNAPPING / RELEASED

A slot maps to exactly one acoustic edge. Freeform arbitrary placement is illegal.

### 4.2 Reach and grab
Player may start manipulation only while:
- inside the visible handle/reach volume;
- not failed;
- not in an uninterruptible objective interaction;
- barrier rail path is not physically blocked by a content-defined hard obstruction.

On grab:
1. player enters `BARRIER_MANIPULATION`;
2. normal locomotion becomes constrained to the local manipulation envelope;
3. world simulation and listeners continue in real time;
4. current and candidate acoustic effects remain previewable.

### 4.3 Move / rotate / snap
Barrier movement follows its authored rail, not mouse-world free placement. Controller and mouse both select direction along the same rail state space.

While between slots, the barrier has **no acoustic attenuation effect** unless its physical panel fully covers a slot's opening according to the deterministic snap envelope. This prevents ambiguous partial attenuation. Prediction explicitly shows the old edge reopening before the new edge becomes blocked.

At snap threshold, the barrier enters `SNAPPING`; on the next canonical fixed step it atomically claims the target slot and applies +3 attenuation to that edge.

If a rail has orientation variants, rotation is discrete and only allowed at authored rotation stations. Orientation changes presentation/physical fit, not attenuation magnitude unless a later content schema explicitly freezes a visible variant.

### 4.4 Release / interruption
Player can voluntarily release at any time. If released between slots, barrier deterministically returns to the nearest legal snap slot; exact midpoint ties return to the last occupied slot. During return it has no attenuation until snapped.

If a listener reaches/fails the player during manipulation, failure interrupts immediately and barrier state is restored by checkpoint reset. No special struggle/combat state.

If a door or moving object would make the target slot invalid during a move, the move is stopped before the invalid envelope and player may release/reverse. Content must not require timing a barrier through nondeterministically moving obstructions.

### 4.5 Exposure contract
Manipulation does not pause listener movement/reactions. The player therefore pays spatial exposure and travel cost for acoustic edits. The design must not add a separate mana/cooldown cost merely to force barrier variety.

## 5. Doors and graph mutation

Door baseline states: `OPEN`, `CLOSED`. A door state is visible in world and changes both physical traversal and its acoustic edge on the same canonical tick.

Baseline rule:
- OPEN: edge enabled with authored base attenuation.
- CLOSED: edge disabled for propagation and traversal.

If Phase 5 needs a sound-leaking closed door, it must be a visibly distinct reusable door archetype, not a per-level exception. The simpler disconnected baseline is canonical until such an archetype is justified.

Door transitions caused by objective/player/listener action commit before sound events generated by that same action if the action fiction physically opens the door first; otherwise the event's explicit `emission_phase` is authored as BEFORE_MUTATION or AFTER_MUTATION. Only these two choices exist and preview displays the selected result.

## 6. Listener state machine

### 6.1 States
- `POSTED` — stationary or following a deterministic short patrol route; can hear.
- `INVESTIGATE` — has accepted a heard event and moves toward its investigation target.
- `ARRIVED/SEARCH` — brief bounded inspection at target; no random wandering.
- `RETURN` — deterministic return to posted route/anchor.
- `ALERT_FAIL` — player has been directly detected under encounter fail rules.

No health, combat, takedown or suspicion bar pillar.

### 6.2 Heard-event selection
Each sound event has stable `event_id`, strength, source node and emission tick. At one resolution tick a listener may hear multiple events. It selects exactly one investigation target using:
1. highest **remaining intensity at listener**;
2. if tied, most recent emission phase/order within tick;
3. if tied, lowest stable `event_id`.

A newly heard event can retarget a listener already in INVESTIGATE/RETURN only if its remaining intensity is **strictly greater** than the intensity that caused the current investigation, or if the current target has already reached ARRIVED/SEARCH. This prevents cheap equal-strength ping-pong juggling.

### 6.3 Investigation target
The target is the sound event's physical source location/node at emission time, not the source's later position. Listener follows a deterministic authored navigation route. Acoustic propagation determines whether it heard the event, not an omniscient shortest path to the player.

### 6.4 Search/return
Search is a short fixed-duration authored state (baseline balance target 1–3 seconds) used for readability, not random cone sweeping. After search, listener returns deterministically unless a stronger valid event retargets it.

### 6.5 Direct detection / failure
Hearing alone does not instantly fail the encounter. Failure occurs only when an encounter's visible direct-detection rule is met, normally listener reaches line-of-sight/proximity detection of player in a forbidden state/zone. Direct detection must be deterministic and separately previewable where relevant.

A listener investigating the *correctly intended* lure is therefore useful rather than a disguised fail meter.

## 7. Exact deterministic update ordering

All gameplay uses a fixed simulation step. Rendering may interpolate but cannot affect rules.

Canonical step order:
1. **Capture inputs** for this tick.
2. **Resolve player movement** and acoustic-node ownership.
3. **Resolve barrier manipulation movement** up to, but not including, snap mutation.
4. **Resolve physical interaction progress** and determine pending door/object mutations.
5. **Commit barrier snaps/releases** atomically.
6. **Commit door/object graph mutations** in stable object-ID order.
7. **Advance moving environmental source positions/node ownership** in stable source-ID order.
8. **Advance listener physical movement/state timers** using their state from tick start; update their acoustic-node ownership.
9. **Generate sound events** due this tick from locomotion, distractions, objective actions and moving sources, with explicit BEFORE/AFTER mutation semantics already converted to the appropriate graph snapshot.
10. **Solve acoustic propagation** for each event using the exact graph snapshot assigned to it.
11. **Resolve listener hearing/event selection** in stable listener-ID order.
12. **Resolve direct-detection/fail conditions** from post-movement positions.
13. **Resolve objective/win conditions** if no fail occurred.
14. **Publish prediction/resolution telemetry** for UI and tests.
15. Advance tick counter.

### Preview equivalence rule
Prediction is not a second approximation. It invokes the same propagation/hearing functions on a cloned prospective state after applying the player's highlighted candidate action/mutation at the same canonical ordering point. If an action depends on future listener motion beyond the immediate deterministic preview horizon, UI distinguishes `current-event hearing result` from longer-term movement consequence rather than pretending certainty.

**Hard acceptance:** for identical canonical state + candidate action, preview listener-hearing booleans must equal actual resolution 100%.

## 8. Prediction mechanical contract

The mechanical data exposed to presentation is:
- source node and strength band;
- every enabled minimum-cost route used to each relevant listener;
- attenuation/intensity band on traversed passages;
- listener threshold band;
- predicted `HEARS / DOES_NOT_HEAR` per relevant listener;
- which edge currently receives barrier attenuation;
- candidate edge while barrier is being moved;
- reason for any blocked/invalid barrier move;
- if door mutation changes the event snapshot, whether emission is before or after mutation.

No hidden `maybe heard` state exists in deterministic baseline play.

Preview for footsteps may show the next locomotion pulse from the player's current/candidate node. Preview for a distraction/objective action appears when that interaction is targetable. Players are not required to memorize numbers.

## 9. Encounter objective, win/fail, checkpoint/recovery

### 9.1 Encounter structure
Each encounter has:
- start state;
- one or more ordered/unordered objective flags;
- extraction/exit condition;
- optional mastery predicates;
- one or more safe checkpoint snapshots only when encounter length warrants them.

Win: required objectives complete and player reaches extraction/exit state.

### 9.2 Fail
Canonical fail families only:
- direct listener detection/capture;
- explicit lethal environmental hazard if visually obvious and justified by content;
- irreversible objective failure only when immediately legible.

Being heard is **not** itself a generic fail.

### 9.3 Restart
Quick restart restores the latest canonical checkpoint snapshot: player/listener/source transforms and states, doors, barrier slot, objective flags, timers, event counters and RNG state if any. Baseline mechanics require no gameplay RNG; content should remain deterministic.

Restart is immediate enough to support learning. It does not preserve post-checkpoint knowledge flags that alter simulation.

### 9.4 Checkpoint placement
Normal 6–12 minute encounters should usually need 0–1 internal checkpoint. Checkpoints occur only in authored safe transition states, never mid-barrier move or mid-sound event. Mastery scoring can require full-encounter clean runs without changing base completion.

## 10. Difficulty and mastery variables

Difficulty must preserve causal logic. Allowed tuning dimensions:
- physical traversal speed / listener movement speed, if both preview and reaction windows remain deterministic;
- manipulation snap generosity and interaction reach;
- direct-detection forgiveness radius/hold duration;
- number/layout of acoustic routes and listeners through content selection;
- sound strength/threshold combinations, always visibly encoded;
- optional preview persistence/animation speed;
- checkpoint density.

Disallowed difficulty tricks:
- hiding acoustic routes or thresholds;
- making prediction inaccurate;
- random hearing;
- longer patrol waits as the primary challenge;
- audio-only cues;
- arbitrary barrier cooldown/mana.

Mastery predicates may include:
- no restart;
- time target;
- barrier-edit budget;
- deliberate selective-audibility target (specific listener hears while another does not);
- low passive-wait percentage where measurable;
- optional fast-move usage.

Mastery may reward efficiency but cannot define a different hidden rule set.

## 11. Exploit attacks and mechanical countercontracts

### 11.1 Nearest-door blocking
**Attack:** park barrier on nearest guard-facing opening and leave it there.

**Countercontract:** mature content must use alternate routes, threshold differences, graph mutation or deliberate lure requirements. Mechanics do not add artificial slot decay. Phase 5 validators should flag mature encounters where one slot makes all completion-critical sounds inaudible to every dangerous listener throughout the solution.

### 11.2 Silence-everything play
**Attack:** always WALK/IDLE, never create useful sound.

**Countercontract:** required campaign encounters include actions that must be heard by a chosen listener, plus unavoidable loud objectives. Hearing is a tool, not merely punishment.

### 11.3 Safe barrier camping
**Attack:** manipulate only from perfectly safe pockets and solve graph before moving.

**Countercontract:** barrier is local/direct and world continues. Mature layouts place some meaningful manipulation envelopes in traversal/exposure relationships. Do not solve this with arbitrary timers.

### 11.4 Infinite lure loop / listener juggling
**Attack:** spam equal distractions to keep listeners permanently displaced.

**Countercontract:** retarget while investigating requires strictly greater received intensity until ARRIVED/SEARCH. Repeating the same equal-strength lure cannot endlessly reset travel. Content may also make distraction sources single-cycle/reset by visible physical state, but no global cooldown is required.

### 11.5 Strongest-sound spam
**Attack:** always use strength-4 distraction because stronger is better.

**Countercontract:** stronger sound reaches more listeners/routes and is therefore not monotonically safer. Content must make over-propagation a real cost. Source strengths are tied to physical actions; player does not freely choose 1–4 from a menu.

### 11.6 Barrier midpoint exploit
**Attack:** hover barrier between slots to somehow block both/neither opportunistically.

**Countercontract:** between slots barrier has no attenuation. Only one snapped slot is active.

### 11.7 Door-state race
**Attack:** exploit frame ordering so preview assumes one door state and hearing resolves another.

**Countercontract:** fixed ordering + explicit BEFORE/AFTER emission phase; same function powers preview and resolution.

### 11.8 Restart brute force
**Attack:** rapidly try every slot without reasoning.

**Countercontract:** fast restart remains required; do not punish experimentation with load time. Instead keep candidate slots legible, use causal preview, and design mature states where several edits/sequences interact. Optional mastery can reward low edits/no restart. If brute force remains more efficient than reading state, that is a content failure, not justification for restart friction.

## 12. One-week implementation/graybox acceptance gates carried forward

A minimal graybox must test 8–12 encounters with this exact mechanical model.

Hard/major-redesign gates:
1. **Prediction parity:** 100% hearing-result agreement between preview and actual deterministic resolution.
2. **Mute parity:** muted testers can make the same optimal mechanical decisions.
3. **Silence dominance:** fail if representative mature content is routinely solved by permanent nearest-door blocking + minimizing sound.
4. **Waiting dominance:** passive waiting >25% of successful representative run time is a major failure; target <10–15% mature.
5. **Verb scarcity:** meaningful barrier edits worse than ~1/minute for long representative stretches is a major failure.
6. **Physical fantasy:** if users primarily describe play as graph editing rather than physically controlling who hears them, redesign presentation/manipulation before adding systems.
7. **Selective audibility comprehension:** test set must teach that one listener hearing can be correct.
8. **Tactile friction:** local barrier interaction must not feel like downtime between stealth decisions.
9. **Content collapse:** 8+ test encounters must be constructible without bespoke acoustic exceptions.
10. **Listener-juggle exploit:** equal-strength repeated lures must not create indefinite displacement.
11. **Ordering audit:** door/barrier/source mutations must reproduce identically under fixed-step replay.
12. **Recovery audit:** checkpoint restore must reproduce graph, listeners, barrier and next-event prediction exactly.

## 13. Mechanical scope exclusions

Phase 4 explicitly does **not** add:
- combat/takedowns/health;
- inventory/crafting;
- multiple freely controlled barriers;
- microphone input;
- continuous realistic wave simulation;
- frequency/pitch puzzle layers;
- random listener hearing;
- suspicion meters with hidden modifiers;
- remote graph-control UI;
- arbitrary physics destruction;
- stealth crowds;
- procedural mission generation requirement.
