## Purpose
Deeper falsification of the five Run-1 finalists. This pass requires concrete mature puzzle families, an explicit dominant-strategy counterfixture, a 15-second trailer beat, demo structure, differentiation proof, scope bounds, and one existential prototype question. A concept survives only if the same compact primitive vocabulary supports several genuinely different reasoning families.

## Fresh market evidence used in this pass
Fresh 2026 checks sharpen two collision risks:
- `A Little Perspective` (released 2026-04-03) explicitly builds 200+ puzzles around line-of-sight, object permanence and perspective changing reality. This does **not** duplicate Last Known Shape's proposed persistent remembered-form authority, but it raises the differentiation burden: Game #007 cannot sell merely as `perspective changes geometry`.
- `Causal Loop` (released 2026-04-23) records/replays up to three past selves, while current programming puzzle `Code, Solve, Revolt!` (released 2026-06-26) foregrounds drag-and-drop programming. Therefore Recurrence Department must remain room-bound semantic recurrence rather than clone replay, and Command Lag must remain embodied delayed causality rather than code construction.

The pass therefore scores **causal skeleton**, not surface novelty.

# 1. G7C01 — DECOMMISSION

## Compact primitive set
- subsystem: RUNNING / RETIRED;
- directed support requirement;
- explicit fallback relation;
- bounded stored state / residual charge token;
- atomic irreversible RETIRE action;
- visible safety predicate for current state.

No bespoke subsystem minigames are allowed.

## Three mature puzzle families
### D-A — Sacrificial redundancy
Two apparently redundant support branches feed a critical cooling/load sink. The obvious leaf-first plan consumes the branch needed to absorb the transient state of a later internal retirement. Correct play retires an internal converter first while a leaf remains alive as temporary fallback, then removes the leaf later.

Reasoning: preserve an apparently disposable capability because **retirement order changes what redundancy means**.

### D-B — Residual-state handoff
A retired pump/actuator stops producing but leaves one bounded stored-state fact that can be discharged only through a still-running neighbor. Retiring the neighbor first traps unsafe residual state. The player must deliberately retire the source before its apparent support.

Reasoning: shutdown asymmetry / post-retirement consequence.

### D-C — Fallback inversion
A subsystem's failure/retirement causes a deterministic fallback controller to assume a different dependency path. The player needs that fallback state because it makes a previously central component independent enough to retire.

Reasoning: use **loss itself to rewrite operational dependency**, not merely peel a graph.

These are materially distinct but the latter two add semantic complexity. The design is viable only if stored-state and fallback remain global reusable primitives, not authored exceptions.

## Dominant-strategy counterfixture
Fixture: A supports B and C; B is a leaf load but also the only safe sink for A's residual state; C can run on fallback after A retires. Leaf-first (`retire B`) makes A permanently unsafe to retire. Correct order is A -> B/C cleanup. This falsifies ordinary reverse-topological leaf stripping under the proposed global rules.

## 15-second trailer beat
0–3s: compact physical plant, five machines visibly running; player highlights one central converter and preview shows several consequences.
3–6s: player permanently pulls its retirement handle; converter goes dark.
6–10s: a fallback path physically engages, one machine changes route, a warning on another clears.
10–13s: player retires a component that was previously marked unsafe.
13–15s: wide shot: half the plant is dark, objective reads `SAFE SHUTDOWN 5/8`, with the remaining live cluster visibly transformed.

Good cause/effect, but the fantasy still risks looking like power-network management.

## Minimum viable demo
5 cases / ~20–30 min:
1. irreversible retirement literacy;
2. dependency preview;
3. redundancy consumed deliberately;
4. residual-state ordering;
5. fallback inversion finale.

## Not-the-analogue / not-the-portfolio test
- Not Decommission Protocol: no exploration-horror or floor minigames; entire game is systemic irreversible retirement ordering.
- Not Tension Budget: no conserved scalar budget and no continuous load allocation.
- Not Stitchspace: player never rewires arbitrary adjacency; relations change only through authored operational fallback after irreversible retirement.

Still, the abstract skeleton remains `network state changes after removing nodes`, which sits closer to existing factory systems than ideal.

## Scope floor / ceiling
Floor: 24 authored shutdown cases, 5 subsystem behaviors, 3 reusable global dependency primitives.
Ceiling: 36 cases, 6–7 behaviors, no narrative exploration layer, no bespoke minigames, no freeform plant construction.

## Existential prototype question
**Can players predict why a retirement is safe/unsafe from the physical scene without falling back to a detached dependency graph?**

If no, kill.

## Run-2 verdict
**ELIMINATE FROM FINAL THREE.** Mechanically valid after the counterfixture, but it pays substantial readability cost to escape leaf stripping and remains too close to network/dependency reasoning already represented in the portfolio. Keep as exclusion history.

# 2. G7C02 — LAST KNOWN SHAPE

## Critical semantic repair before examples
Free-camera silhouette interpretation is rejected. The concept survives only with **authored Observation Frames**. Each frame exposes a deterministic discrete observation transform. Entering/activating a frame previews the exact candidate remembered form before commit. No pixel matching, hidden computer vision, or precision camera alignment.

Primitive set:
- object with current local physical state;
- bounded remembered-form slot;
- authored Observation Frame with deterministic transform/mask;
- OBSERVE commit overwrites remembered form;
- when outside direct observation, remembered form becomes the object's authoritative collision/affordance state under explicit rules;
- re-observation can overwrite it.

## Three mature puzzle families
### L-A — Preserve versus overwrite
A long remembered plank-form bridges a gap, but the same object must later be remembered as a short block to fit a lift cage. The player must exploit the long form, reposition the object, then intentionally overwrite memory at a second frame.

Reasoning: remembered state is useful but not universally best; **when to overwrite** matters.

### L-B — Occlusion composition
An Observation Frame contains a fixed foreground mask. A multi-lobed object viewed through it commits a deterministic partial silhouette/form class. That remembered form can press two separated contacts but cannot pass a narrow slot. Another frame produces the inverse affordance.

Reasoning: choose observation transform based on downstream affordance, not largest shape.

### L-C — Coupled observation order
Two objects share a frame region where one can serve as an authored occluder for the other. Observing A first changes A's authoritative form; moving A then exposes a different legal observation of B. Later re-observing A would destroy the bridge needed for B's return route.

Reasoning: **observation order and preservation across multiple objects**.

All three use the same OBSERVE/overwrite vocabulary; no new magical verbs are required.

## Dominant-strategy counterfixture
Object O has three legal remembered forms: LONG, TALL, COMPACT. LONG reaches a bridge target but physically blocks the only route to the Observation Frame that can produce COMPACT. Correct solution uses TALL first to actuate a lift, COMPACT to traverse, then LONG only after the player has relocated to the far side. `Find biggest silhouette and keep it` fails deterministically.

## 15-second trailer beat
0–3s: player stands at a marked viewing frame; a chunky object beyond a shaped foreground mask previews as a long bridge silhouette.
3–5s: press Observe; outline flashes and locks.
5–8s: player steps away; the object physically resolves into the remembered long form and spans a gap.
8–11s: cross it, reach a second frame from another side; preview shows a compact form.
11–13s: Observe again; bridge collapses into compact block behind player.
13–15s: block now fits a socket/lift and activates it. Text-free causal beat.

This is the strongest trailer proof of the field.

## Minimum viable demo
6 cases / ~20–30 min:
1. one object, one frame, remembered form becomes physical;
2. overwrite literacy;
3. same object, two useful forms;
4. fixed occlusion mask;
5. two-object observation order;
6. finale requiring preserve -> exploit -> overwrite -> exploit.

No free-camera perspective puzzle appears in demo.

## Not-the-analogue / not-the-portfolio test
- Not A Little Perspective: rotating viewpoint does not continuously rewrite geometry; only explicit authored Observation Frames commit a persistent remembered form, and leaving observation is essential.
- Not Superliminal-style perspective scaling: no arbitrary size-from-camera manipulation.
- Not Stitchspace: no adjacency rewiring.
- Not False Map Department: no representation-inspection bureaucracy; observation directly writes physical object state.

The concept owns a different causal sentence: **`What the object was last observed as becomes what it physically is when unobserved.`**

## Scope floor / ceiling
Floor: 28 cases; 4 reusable object archetypes; 5–7 authored observation transform/mask families; 1–2 objects in most cases.
Ceiling: 36 main cases + 6 mastery remixes; max 3 simultaneously relevant remembered objects; no arbitrary image recognition, free-camera commit, recursive perspective, combat, platforming dexterity, or procedural level generation.

## Existential prototype question
**After one tutorial example, can a player correctly predict the exact committed remembered form from the preview/frame before pressing Observe, and explain why it changed?**

If predictability is weak, the whole concept becomes quantum-magic trial-and-error and must die.

## Run-2 verdict
**ADVANCE — FINAL THREE.** Strongest visual/store hook, low portfolio collision, and three distinct mature reasoning families survive once observation is discretized. Technical/readability prototype risk remains existential.

# 3. G7C03 — COMMAND LAG

## Compact primitive set
- direct physical machine commands;
- integer turn/event delay per command target;
- visible bounded pending queue;
- deterministic maturation order;
- player movement/interactions consume steps where declared;
- commands may have explicit state preconditions at issue and/or maturation;
- optional CANCEL only as a globally specified scarce/limited rule if retained later.

No code blocks, loops, variables, scripting language or `Run Program` mode.

## Three mature puzzle families
### C-A — Arrival synchronization
Player issues `OPEN` to a remote gate with delay 3, then physically traverses two local actions so the gate opens exactly as a moving carrier arrives. Issuing later misses the carrier; issuing earlier causes the gate to close/reset before arrival.

Reasoning: align future machine state with embodied travel.

### C-B — Future-legality inversion
A command can be issued only while sensor S is currently clear, but when it matures its effect depends on the then-current machine state. Player must issue before moving a crate onto S, knowing the delayed command will mature after another machine has changed state.

Reasoning: distinguish **issue-time legality from maturity-time consequence**.

### C-C — Queue interference
Two commands to the same actuator mature in stable order while a third device changes which transition is useful. The solution intentionally queues an apparently contradictory future action because an intervening consequence changes the actuator's semantic result.

Reasoning: overlapping pending consequences, not just hit-the-timing-window.

All remain direct physical scheduling.

## Dominant-strategy counterfixture
Three devices A/B/C. `Queue everything immediately` fails because B's command is issue-legal only after A matures, while C must be issued before A matures because A's result closes C's command access. Correct sequence interleaves issue -> movement -> maturity -> issue rather than front-loading a script.

## 15-second trailer beat
0–3s: player slaps a physical `OPEN` lever; a three-notch luminous delay track appears on the door itself.
3–6s: player runs/steps to another machine and issues `ROTATE` with a shorter two-notch delay.
6–9s: one step advances both; ROTATE matures first, physically redirecting a carrier.
9–12s: next step: OPEN matures exactly as carrier reaches the gate.
12–15s: carrier passes and powers exit; compact on-world countdowns make the causal overlap legible.

Strong, though less immediately magical than Last Known Shape.

## Minimum viable demo
6 cases / ~25–35 min:
1. one command / fixed delay;
2. movement advances delay;
3. two different delays;
4. issue-time versus maturity-time state;
5. anti-frontload fixture;
6. three-command overlapping finale.

## Not-the-analogue / not-the-portfolio test
- Not Code, Solve, Revolt! or generic programming games: no program construction, loops, variables, code canvas or prewritten script; every command is issued to a physical machine from the live world.
- Not Recurrence Department: commands target machines explicitly and wait in queues; locations do not automatically replay past actions.
- No prior factory game uses future command maturity as its primary state variable.

## Scope floor / ceiling
Floor: 30 cases, 5 machine verbs, delays 1–4, max 3 pending commands in early/mid game and 4 in proven late cases.
Ceiling: 40 cases, 7 machine verbs, max visible horizon 5, no real-time milliseconds, no scripting language, no automation construction sandbox, no combat.

## Existential prototype question
**Can players plan 3–4 overlapping pending commands from world-space cues without needing a detached timeline spreadsheet?**

If the answer is no, the concept collapses into UI programming and must die or shrink radically.

## Run-2 verdict
**ADVANCE — FINAL THREE.** Best deterministic/systemic implementation profile; concrete mature families resist `queue all then wait`. Presentation burden is the main risk.

# 4. G7C08 — CHAIN OF CUSTODY

## Compact primitive set
- object carries a bounded provenance state, not an event log;
- handler/station applies one visible provenance transform;
- acceptance gates inspect bounded predicates;
- some transforms erase/invalidate prior facts;
- physical handoff/pass is the repeated verb.

## Three mature puzzle families
### H-A — Order-sensitive certification
Object needs WASHED then SEALED; sealing before washing prevents later wash. Straight provenance order puzzle.

### H-B — Mutually exclusive trust domains
Handling by actor Red grants R but destroys B; actor Blue grants B but destroys R; a neutral escrow station can preserve one fact while changing last-handler class. Goal requires different objects to arrive with complementary histories.

### H-C — Contamination/reset route
Passing through one required area marks an object CONTAMINATED; sanitizer clears contamination but also clears a fragile certification. Player must choose where in the physical route certification happens.

These are valid, but the core increasingly resembles finite-state key crafting.

## Dominant-strategy counterfixture
No universal certifier exists; actor A grants AUTHENTIC but invalidates STERILE, actor B grants STERILE only if AUTHENTIC absent, escrow E preserves AUTHENTIC while changing last-handler identity but is inaccessible after sanitation. A simple `route everything through best actor` policy cannot solve both target objects.

## 15-second trailer beat
0–4s: physical parcel passes from gloved worker to scanner; two large icon-stamps appear directly on parcel.
4–7s: another worker grabs it; one stamp visibly tears off and a new seal appears.
7–11s: player tries secure gate; gate rejects with the missing stamp icon.
11–15s: Undo, pass through intermediary, parcel arrives with the correct two-icon history and gate opens.

Readable, but less emotionally/magically distinctive than the other finalists.

## Minimum viable demo
5 cases: last-handler rule; ordered two-fact rule; destructive handler; sanitizer/reset; two-object finale.

## Not-the-analogue / not-the-portfolio test
Not Organism Cargo only if routing distance/throughput is irrelevant and the puzzle is purely about transformation history. Not colored-key inventory only if order/destructive provenance remains essential. Unfortunately the mature examples repeatedly converge on `apply finite-state transforms in correct order`, a familiar abstract skeleton.

## Scope floor / ceiling
Floor: 28 cases, <=4 provenance facts visible per object, <=5 transform types.
Ceiling: 36 cases, <=5 facts, <=7 transform types, max 3 active objects, no text audit logs, no procedural bureaucracy simulation.

## Existential prototype question
**Does physical provenance feel like a new game verb after 30 minutes, or does the player simply perceive stamps as colored keys/status effects?**

## Run-2 verdict
**ELIMINATE.** It is implementable and deterministic, but the strongest mature fixtures expose the concept as finite-state transformation/order puzzles with bureaucratic skin. The final field has more ownable causal fantasies.

# 5. G7C10 — RECURRENCE DEPARTMENT

## Semantic repair
Avoid recorded clones entirely. A room stores at most one bounded **semantic recurrence token** created by a qualifying player action performed in that room. At the next declared turn boundary, the room itself repeats that action against its current local target mapping. Presentation is architectural: room fixtures pulse/animate; no ghost avatar reenacts player motion.

Primitive set:
- discrete rooms;
- qualifying semantic actions (PRESS / TURN / TRANSFER-like small vocabulary, exact set later);
- one-turn room-bound recurrence token;
- deterministic local target mapping;
- explicit overwrite/cancel rule;
- stable simultaneous recurrence ordering;
- turn-based player movement/action.

## Three mature puzzle families
### R-A — Seed for future state
Press a room lever now; leave. Before its recurrence fires, move an object so the same room-local semantic action affects a different currently mapped target. The repeat is useful because **world state changed between seed and recurrence**.

### R-B — Harmful recurrence avoidance
A required action will recur next turn and would undo/damage progress. Player must arrange a blocker/state change, overwrite the room token with another qualifying action, or exploit the harmful repeat elsewhere. Extra echoes are liabilities, defeating `seed everything then wait`.

### R-C — Recurrence cascade
Action in room A seeds recurrence A. Player moves to B and acts. At the next boundary A's recurrence changes a local routing/state condition so B's recurrence on the following turn has a different semantic target. No echo directly records another echo as a player action; the cascade is through world state, preventing unbounded recursion.

Reasoning: overlapping delayed local obligations.

## Dominant-strategy counterfixture
Rooms A/B both have pending repeats. Waiting causes A to close the path before B's useful recurrence can affect its target. Seeding all rooms immediately creates an unavoidable bad recurrence. Correct play seeds A, changes B's local mapping, overwrites A's token with a harmless semantic action, then seeds B. This directly kills `activate everything and wait`.

## 15-second trailer beat
0–3s: player presses a chunky wall lever in Room A; room border gains a single `next turn` pulse.
3–6s: player walks into adjacent Room B and pushes a crate onto a selector.
6–9s: turn advances; **Room A itself** flashes and its lever depresses with no ghost/player clone; machinery in B reroutes.
9–12s: Room B now pulses from the player's prior push/action and fires its own local consequence.
12–15s: exit opens while Room A begins telegraphing a now-dangerous next recurrence. Trailer caption could be `ROOMS REMEMBER WHAT YOU DO.`

Very legible if room identity and one-turn bound are visually strong.

## Minimum viable demo
6 cases / ~25–35 min:
1. room repeats one lever press next turn;
2. world state changes target before recurrence;
3. harmful repeat;
4. overwrite/cancel literacy;
5. two pending rooms with stable order;
6. small state-mediated cascade finale.

## Not-the-analogue / not-the-portfolio test
- Not Causal Loop: no recorded path, no past-self avatar, no clone coordination, no re-recording timeline.
- Not Echoed-like replay: recurrence belongs to location and repeats semantic local action once at a bounded boundary.
- Not Command Lag: player does not command a machine to act later; the *room automatically remembers the action performed there* and imposes a future recurrence.
- No prior factory game centers mandatory future consequences created by location memory.

## Scope floor / ceiling
Floor: 28–32 cases, 3 qualifying action classes, max 2 simultaneous pending recurrences through most campaign.
Ceiling: 38 cases, 4 action classes, max 3 pending recurrences in proven late cases, no clone avatars, no freeform recording, no arbitrary action replay, no real-time timing, no unbounded echo recursion.

## Existential prototype question
**Can players understand, at a glance, which room will repeat which semantic action next turn without mentally maintaining a timeline?**

If not, kill.

## Run-2 verdict
**ADVANCE — FINAL THREE.** Strong deterministic depth and low production burden. Market collision with temporal-echo language remains manageable only if the architectural/location-bound identity survives prototype testing.

# Final-duel requirements
The next pass must compare only these three using concrete equivalent evidence rather than more adjectives.

For each finalist build:
1. **six canonical case blueprints** spanning tutorial, early, mature A/B/C and late synthesis;
2. exact **primitive-count growth** from tutorial to late game;
3. a paper **state model** sufficient to expose determinism/solver risk;
4. a likely **player-error taxonomy** — whether failure is explainable or feels arbitrary;
5. explicit **hour-4 repetition attack**;
6. production estimate by relative authoring/art/QA burden;
7. demo-to-full conversion thesis;
8. store capsule / one-sentence / 6-second silent-GIF test;
9. direct head-to-head scoring with a **selection threshold**, not a three-way tie.

Selection threshold: winner must have no unresolved paper-level fatal flaw and must lead the other two on at least **two of three** axes: (A) ownable hook/market legibility, (B) systemic depth without bespoke-rule growth, (C) implementation/content risk. Prototype-only unknowns may remain as explicit empirical gates.

If one concept clears the threshold, select it and immediately begin Phase 3 Product Thesis Lock in the same run. If none clears it, kill/rework rather than force a winner.
