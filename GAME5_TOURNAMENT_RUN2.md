# 3. G5C02 — Tension Budget constrained graybox

## 3.1 Hard vocabulary ceiling
Exactly three reusable load archetypes are allowed for this pass:

### L1 — Lift
A platform moves among three obvious authored heights as its cable is SLACK / TAUT / HIGH.

### L2 — Counterweighted Gate
A gate/counterweight assembly occupies three obvious authored positions under SLACK / TAUT / HIGH. Mounting orientation can be mirrored spatially, but the response language remains the same archetype.

### L3 — Flexible Span
A cable-supported bridge/span has three authored postures: deep sag / usable level / over-lifted-steep. The geometry itself communicates state; there is no continuous rope-physics solution space.

Other visible machinery may carry the cable or decorate the facility, but it may not introduce a fourth mechanical response family.

Other frozen limits remain:
- one player-controlled anchor;
- 3–5 authored sockets/rail commits;
- 2–4 active loads;
- only SLACK / TAUT / HIGH cable bands;
- one ordinary objective may visibly add/remove one load;
- no numeric tension UI;
- no detached cable graph;
- no free rope construction;
- no hidden tension state.

## 3.2 Twelve mature states under only three load archetypes

### T01 — Gate for Lift
Loads: L1 + L2.
One socket raises the lift but drops the gate. Player must choose which route exists first.

Reasoning: collateral tradeoff.
Static socket enumeration risk: **HIGH**. Acceptable only as early teaching.

### T02 — Span Compromise
Loads: L1 + L3.
Extreme sockets either keep the lift reachable but leave the span sagging, or flatten the span while placing the lift too high. Middle distribution is required.

Reasoning: threshold compromise.
Enumeration risk: **MEDIUM**; world posture should make the compromise reason readable.

### T03 — Three-Load Middle
Loads: L1 + L2 + L3.
The obvious local gate is open at two sockets, but only one leaves the span traversable and lift reachable.

Reasoning: equivalent-local / different-global.
Enumeration risk: **MEDIUM** if all sockets are safely reachable; later campaign should physically couple traversal.

### T04 — Ride Then Reconfigure
Loads: L1 + L2.
First distribution raises the lift so the player can ride to a balcony. From that new player position the gate state matters differently, requiring a second anchor placement.

Reasoning: traversal coupling + sequence.
Enumeration risk: **LOW** because the whole solution is not visible from one static state.

### T05 — Span Crossing Locks Position
Loads: L2 + L3.
Flattening the span lets the player cross to the far side. The next useful anchor approach is only reachable after crossing, so the second placement cannot be chosen from the starting safe pocket.

Reasoning: physical sequencing.
Enumeration risk: **LOW**.

### T06 — Lift / Span / Gate Relay
Loads: L1 + L2 + L3.
Placement A reaches a central lift; B flattens the span from that platform; C restores gate clearance for exit.

Reasoning: three-placement sequence preservation.
Enumeration risk: **LOW**.

### T07 — Counterweight Removed
Loads at start: L1 + L2 + L3. Objective visibly detaches the L2 counterweight/load. The same anchor socket now redistributes the remaining budget differently.

Reasoning: load mutation.
Enumeration risk: **LOW** because pre-objective testing does not reveal post-mutation consequence.

### T08 — Span Added
Loads at start: L1 + L2; objective visibly connects a suspended span as a third load. Extraction requires reading the new posture distribution.

Reasoning: topology/load mutation + return planning.
Enumeration risk: **LOW**.

### T09 — Local Gate Trap
Loads: L1 + L2 + L3.
Two sockets open the nearest gate. One simultaneously over-lifts the span beyond a later landing; only the other preserves the global route.

Reasoning: local equivalence / global consequence.
Enumeration risk: **MEDIUM**, but the correct explanation is visible rather than numeric.

### T10 — Player-as-Commitment
Loads: L1 + L3.
Player rides the lift into a pocket that becomes inaccessible when the anchor returns to the obvious state. The next distribution must be chosen with the player’s future location in mind.

Reasoning: traversal commitment.
Enumeration risk: **LOW**.

### T11 — Return Inversion
Loads: L1 + L2 + L3.
Entry uses a high lift and closed gate. The objective removes one visible load, causing that same socket to over-lift the span on the return path. Extraction needs a previously useless socket.

Reasoning: state mutation + return inversion.
Enumeration risk: **LOW**.

### T12 — Four-Load Finale Within Three Archetypes
Loads: two L1 instances + one L2 + one L3.
No new response family. The player performs three meaningful placements: reach a raised platform, preserve a gate while crossing the span, then reconfigure after one lift detaches from the system.

Reasoning: collateral tradeoff + sequence + repeated archetype interaction + mutation.
Enumeration risk: **LOW** if camera/world layout does not expose all later states from the start.

## 3.3 Static-socket-enumeration measurement
Of the 12 mature/teaching states:
- clearly reducible to static socket enumeration: **1/12** (T01);
- partially enumerable but still asks multi-consequence reading: **3/12** (T02, T03, T09);
- requires traversal sequence and/or visible load mutation beyond one static socket table: **8/12**.

This passes the paper depth test **without a fourth load archetype**.

Important caveat: exact preview can still make a poorly authored mature room trivial if the player can stand safely at one anchor and inspect every socket. Later content rules must reject that layout, not hide consequences.

## 3.4 Nonnumeric readability attack
The model remains readable on paper if each state is mechanical posture, not a hidden scalar:
- SLACK = visibly hanging cable + relaxed load posture;
- TAUT = straight cable + mid/load-working posture;
- HIGH = straight/strained cable + clearly extreme load posture;
- the three archetypes must be recognizable by silhouette at ordinary gameplay scale;
- changes occur together while the anchor moves, showing collateral consequence in one view where possible.

No number is needed to solve any T01–T12 state. If implementation needs a number to disambiguate two visually identical postures, the content is invalid.

# 4. G5C37 — Zero-G Tool Orbit constrained graybox

## 4.1 Hard vocabulary ceiling
Exactly:
- one carried tool;
- two orbit-track shapes: **RING** and **OVAL**;
- at most three reusable tool/world relationships:
  1. **STRIKE TARGET** — tool crossing a marked target causes a short deterministic activation;
  2. **INTERCEPT HAZARD** — tool crossing a marked hazard lane blocks/intercepts one pulse/projectile family at that moment;
  3. **CATCH / TRANSFER ZONE** — player can recover the tool or hand it to another anchor through a generous authored capture region;
- authored local tracks only;
- no real orbital simulation;
- no second tool;
- no weapon/combat branch;
- no ballistic free-aim requirement.

Track radius/orientation and anchor placement may vary as level geometry, but do not create additional relationship types.

## 4.2 Twelve mature states under one tool / two tracks / three relationships

### O01 — Repeating Strike
One RING track repeatedly crosses a strike target, opening a door pulse each cycle.

Reasoning: first periodic actor lesson.
Parking risk: **HIGH**; teaching only.

### O02 — Ring vs Oval
RING intersects target A; OVAL intersects target B. Player chooses the track that creates the intended route.

Reasoning: track selection.
Parking risk: **MEDIUM-HIGH**; still early teaching.

### O03 — Launch and Cross
Tool strikes a target periodically while the player traverses to the far side and must recover it in a catch zone.

Reasoning: persistent action + independent player movement.
Parking risk: **LOW**.

### O04 — Far-Side Catch
The useful target is hit only long enough for the player to cross. Completion requires catching the tool on the opposite arc before continuing.

Reasoning: catch-position planning.
Parking risk: **LOW**.

### O05 — Anchor Hand-off
Launch on anchor A, cross through its target window, catch in a transfer zone, then release onto anchor B.

Reasoning: physical hand-off.
Parking risk: **LOW**.

### O06 — Intercept Corridor
Tool on an OVAL periodically crosses one hazard lane. Player moves through the corridor during successive safe crossings rather than waiting at the start.

Reasoning: moving coverage + traversal.
Parking risk: **LOW** if route length requires player commitment during the orbit.

### O07 — Strike vs Intercept Tradeoff
RING hits the progress target but does not cover the hazard lane; OVAL covers the hazard but misses the target. Player must use one, recover the tool, then use the other.

Reasoning: sequence across two relationship types.
Parking risk: **LOW**.

### O08 — Moving Strike Window
A strike target rides a simple deterministic mechanism through the OVAL path. The player launches tool, traverses, then catches rather than waiting for repeated target coincidence.

Reasoning: periodic alignment + planned player movement.
Parking risk: **LOW-MEDIUM**. Timing must remain generous; target motion is environmental animation, not a new control system.

### O09 — Transfer Across Hazard
Anchor A’s orbit creates a safe intercept window leading directly into anchor B’s catch zone. The player must physically arrive to recover and transfer before crossing the second hazard region.

Reasoning: interception + hand-off.
Parking risk: **LOW**.

### O10 — Objective Mutation
A visible panel rotates after objective completion and now places a strike target inside the old orbit path, making the previously helpful parked orbit harmful. Player must recover and reassign tool.

Reasoning: state mutation + return inversion.
Parking risk: **LOW**.

### O11 — Two-Anchor Return
Entry uses RING on A then OVAL on B. Objective mutation blocks the original B catch route, so player must recover from a different authored catch zone and return the tool to A.

Reasoning: route/catch planning + return inversion.
Parking risk: **LOW**.

### O12 — Final Three-Placement Chain
One tool only. Placement 1 strikes target A while player crosses. Catch/transfer to anchor B; placement 2 intercepts hazard lane during traversal. Recover at far catch zone; placement 3 uses OVAL to strike extraction target after the objective has changed geometry.

Reasoning: persistent second actor + two transfers + relationship sequencing + mutation.
Parking risk: **LOW**.

## 4.3 Parking-tool measurement
Of 12 states:
- solvable mainly by “choose orbit and leave tool parked”: **2/12** (O01, O02), both appropriate teaching states;
- completion-critical independent player movement while tool remains active: **10/12**;
- completion-critical catch/recovery: **9/12**;
- explicit anchor transfer: **5/12**;
- uses the intercept relationship: **4/12**;
- requires no tool/target family beyond the frozen ceiling: **12/12**.

This clears the paper repetition test better than expected. The risk moves from vocabulary depth to **control feel and catch reliability**.

10–14s — release tool to RING. **Signature action 1: launch.** Tool begins periodic strike.
14–38s — player thrusts through the pulsing door route while tool continues independently.
38–43s — player reaches far-side catch zone and recovers tool. **Signature action 2: catch.**
43–49s — release to OVAL on anchor B. **Signature action 3: transfer/launch.** Tool now intercepts a hazard lane.
49–82s — player crosses the hazard corridor during repeated intercept windows. Movement is continuous; no need to watch a full cycle from safety.
82–87s — catch tool at downstream zone. **Signature action 4.**
87–96s — objective interaction rotates a blocker/target panel, making the old A orbit harmful for extraction.
96–111s — player returns toward anchor C with tool.
111–116s — launch onto RING C. **Signature action 5.** Tool strikes extraction target periodically.

Estimated metrics:
- launch/catch/transfer signature actions: **6 / 180s = 2.0 per minute**;
- player movement while tool independently acts: **~105–120s / 180s**;
- true idle passive waiting: **~3–6%** if cycle lengths are authored tightly;
- execution-error exposure after solution understood: **MEDIUM** because three catches occur; must be reduced empirically with generous deterministic capture;
- explanatory UI time in mature play: **~0–5s** of local track preview, no timeline/orbit math UI.

## 4.5 First-five-minute onboarding attack
Minute 0–1: player releases tool into one clearly highlighted RING; it repeatedly hits a target.
Minute 1–3: player must move through the opened route and catch the tool on the far side.

The product identity is learned through action, not orbit equations.

Kill condition: if players understand the solution but routinely miss catches or ask where the tool will be rather than reading the visible track/ghost, control/prediction has failed.

Tournament-best mute clip remains:

- strikes target and opens route;
- player moves independently across screen while tool keeps looping;
- player intercepts/catches it on the far side and immediately transfers it to a second anchor.

This communicates more action per second than Tension Budget, though the “why orbit?” product explanation is less instantly grounded in everyday physics.

## 4.7 Run-2 verdict
**SURVIVES STRONGLY.**

The one-tool/two-track/three-relationship ceiling still generated 10 mature states that require independent movement and nine that require recovery, so `park wrench on switch` does not dominate on paper.

The remaining existential risk is empirical: controller movement + catch feel must be so forgiving that the puzzle fails for reasoning, not interception dexterity.

Provisional Run-2 pressure score: **88.0/100**.

# 5. G5C21 — Broken Rule Workshop constrained graybox

## 5.1 Hard vocabulary ceiling
Seven reusable machine modules only:
1. **FEEDER** — releases one workpiece;
2. **SENSOR** — exposes simple ON/OFF occupancy/state;
3. **CLAMP** — holds/releases a workpiece;
4. **BELT** — advances workpiece through one lane;
5. **PRESS** — performs the visible process action;
6. **DIVERTER** — sends workpiece left/right;
7. **OUTPUT** — accepts/rejects the final workpiece visibly.

Four binary rule families only:
- DIRECTION — left/right;
- ORDER — A-before-B / B-before-A;
- CONDITION — act on ON / act on OFF;
- DELAY — short/long.

Other hard contracts:
- one deterministic 5–12 second machine cycle;
- exactly one wrong cartridge at baseline;
- cartridge family/slot is physically visible;
- small visible spare set;
- RUN/RESET immediately repeatable;
- no code, truth table, detached wiring board, circuit construction or multiple simultaneous faults.

## 5.2 Twelve machine faults

### W01 — Wrong Diverter Direction
Modules: feeder, belt, diverter, output.
Fault: DIRECTION reversed; workpiece visibly exits into reject tray.
Diagnosability: **very high / near-trivial**.

### W02 — Press Before Clamp
Modules: feeder, sensor, clamp, press, output.
Fault: ORDER; press fires before clamp secures part, part jumps/misaligns.
Diagnosability: **high**.

### W03 — Clamp on Empty
Modules: feeder, sensor, clamp, belt.
Fault: CONDITION; clamp reacts to sensor OFF rather than ON.
Diagnosability: **high**.

### W04 — Early Feed
Modules: feeder, belt, press, output.
Fault: DELAY; second movement begins before press clears.
Diagnosability: **medium-high**.

### W05 — Diverter Before Inspection
Modules: feeder, sensor, diverter, output.
Fault: ORDER; diverter commits route before sensor state arrives.
Diagnosability: **medium**.

### W06 — Belt Reversal
Modules: feeder, belt, clamp, output.
Fault: DIRECTION; belt moves part away from clamp/output.
Diagnosability: **very high / near-trivial**.

### W07 — Press on Sensor OFF
Modules: sensor, clamp, press, belt.
Fault: CONDITION; press cycles on empty station.
Diagnosability: **high**.

### W08 — Late Clamp
Modules: feeder, belt, clamp, press.
Fault: DELAY; clamp engages after part has already passed center.
Diagnosability: **medium-high**.

### W09 — Output Opens Before Diverter
Modules: belt, sensor, diverter, output.
Fault: ORDER; output path closes before diverter completes route.
Diagnosability: **medium**.

### W10 — Reject Direction Inverted
Modules: sensor, diverter, output.
Fault: DIRECTION; correct part goes to reject branch.
Diagnosability: **high**, especially after one run.

### W11 — Sensor Logic Inverted
Modules: feeder, sensor, clamp, belt, output.
Fault: CONDITION; downstream action occurs only when station is empty.
Diagnosability: **medium-high**.

### W12 — Long Reset Beat
Modules: feeder, clamp, press, belt, output.
Fault: DELAY; machine sequence collides because one module holds state too long.
Diagnosability: **medium**.

## 5.3 Reuse and visual-diagnosis measurement
Across the 12 faults:
- all seven modules are reused repeatedly;
- no new module family is required;
- all four rule families contribute multiple faults;
- visually diagnosable after one normal RUN without a logic board: **roughly 9/12**;
- remaining **3/12** plausibly need a second observation/test to separate order from delay/condition timing.

So the vocabulary ceiling itself is not the main failure.

The problem is that high visual diagnosability and the “exactly one wrong binary cartridge” contract create a structural difficulty ceiling.

## 5.4 Brute-force search-space measurement — fatal pressure
With six active cartridge sockets in a representative mature machine and binary cartridges:
- exactly one slot is wrong;
- each slot has exactly one opposite candidate state inside its family;
- a blind player can therefore test at most **6 swaps** to guarantee discovery;
- average discovery under random slot order is about **3.5 tests**;
- at a 5–12 second machine cycle plus a few seconds to swap/reset, blind completion is often roughly **35–80 seconds** even without understanding the machine.

At seven active sockets, worst-case blind search is still only seven swaps. The short RUN loop that makes the concept pleasant also makes brute force unusually cheap.

This is not an authoring flaw that can be fixed by better layouts. It follows from the frozen product rule:
**one wrong binary cartridge + immediate deterministic rerun**.

Potential “fixes” all violate the tournament discipline:
- multiple simultaneous wrong cartridges → changes the central diagnosis contract and expands combinatorics;
- three/four-value rule cartridges → expands vocabulary/UI burden;
- limited attempts, repair currency, punishment timers or run costs → adds an external anti-bruteforce system;
- hiding cartridge families/slots → damages causal readability/fairness;
- longer machine cycles → makes observation slower and worsens the repeated-action target.

Therefore this pass cannot legitimately rescue the weakness.

## 5.5 180-second normal-play trace
Representative fault: W09/W12-class machine.

0–10s — player inspects machine silhouette and presses RUN.
10–20s — watches first full failure chain. Observation is active evidence gathering, not idle patrol waiting.
20–28s — approaches suspected cartridge, swaps it. **Signature action 1.**
28–38s — RUN again. **Signature action 2.** Machine still fails differently or confirms hypothesis.
38–48s — revert/swap second candidate. **Signature action 3.**
48–58s — RUN. **Signature action 4.** Success.
58–80s — move to next machine/short presentation transition.
80–90s — RUN new fault.
90–103s — observe.
103–111s — swap cartridge. **Signature action 5.**
111–121s — RUN. **Signature action 6.**
121–132s — inspect symptom, swap alternate. **Signature action 7.**
132–142s — RUN. **Signature action 8.** Success.
142–180s — next-machine transition / setup / short completion feedback.

Estimated metrics:
- swap/RUN signature actions: **8 / 180s = 2.67 per minute**;
- idle passive waiting: **~0%**, but observation occupies roughly **30–40%** of play time by design;
- execution-error exposure: **LOW**;
- explanatory/icon interpretation burden: **MEDIUM-HIGH** because four rule families must remain immediately readable on physical cartridges;
- blind brute force can mimic or beat much of this cadence.

## 5.6 First-five-minute onboarding attack
The first fault must be obvious enough to teach RUN → symptom → cartridge → rerun. This necessarily teaches the player that every puzzle contains exactly one bad slot and that flipping a cartridge is cheap.

By minute five, an optimization-minded player can already discover the dominant meta-strategy: if diagnosis is uncertain, flip candidate slots one by one. Because every cycle is intentionally short, there is little friction discouraging this.

Adding friction would contradict the product’s best feature.

## 5.7 Mute-store-GIF attack
The clip is clear:
- press RUN;
- machine jams/fails visibly;
- pull one chunky cartridge;
- insert opposite;
- rerun succeeds.

The causal story is strong, but it resembles the broad “repair the logic/machine” product family more than the two surviving competitors resemble their nearest neighbors.

## 5.8 Run-2 verdict
**ELIMINATE G5C21 BROKEN RULE WORKSHOP.**

Reason: it survives the module-reuse test but fails the hostile-strategy test structurally. Under its own frozen small vocabulary, brute-force cartridge flipping guarantees solutions too cheaply. Preventing that requires changing the one-wrong-binary-rule thesis or adding punitive/meta systems. Neither is allowed in a tournament pass.

This is a stronger elimination reason than category crowding or content cost because it arises directly from the central mechanic.

Provisional comparison score after destructive penalty: **77.0/100 / ELIMINATED**.

Do not rescue the concept in Phase 2 by adding more rule values, multiple hidden faults, limited attempts or repair economy.
